# Decisions log

Architecture and platform decisions for Slussen, with the reasoning and the alternative that was rejected.

## Foundations: accounts, identity and cost

| ID | Decision | Why | Alternative rejected |
| --- | --- | --- | --- |
| D1.1 | Repo `slussen`, project folder outside cloud-synced folders | No file locks on venv or Docker files | Documents (OneDrive-synced) |
| D1.2 | Python 3.13 for `venv-pipeline`, alongside system default 3.14 | Broader library support (Snowflake connector, pyarrow, Airflow providers) and a supported Lambda runtime | Python 3.14 (too new for some dependencies) |
| D1.3 | AWS Paid plan + AWS Organizations + IAM Identity Center (organization instance, single-region eu-north-1); permission sets AdministratorAccess, DataEngineer, View-Only | Permission sets need an organization instance; single-region keeps identity data in the EU and avoids a customer-managed KMS key | Free plan with IAM users (would have kept Free Tier credits, which expired when the Organization was created) |
| D1.4 | Snowflake student trial: 120 days, $400 credits, Enterprise, AWS_EU_NORTH_1 | Four times the runway of the 30-day trial; Enterprise enables masking and row access policies | Standard 30-day trial |
| D1.5 | Cortex is blocked on the student trial; add a payment method only shortly before the AI layer is built, behind guardrails | Delays billing exposure until Cortex is actually needed; the AI layer stays in scope | Adding the card at account setup; dropping the AI layer from scope |
| D1.6 | Separate `ADMIN_DB.COST_CONTROL` for account-level cost objects (AI quota) | The data product database can be dropped or rebuilt without touching the guardrails | Cost objects inside `ECOM_DB` |
| D1.7 | Hybrid infrastructure work: create with CLI commands saved in `scripts/bootstrap/`, verify in the console | Reproducible setup in Git while still learning visually; Bash scripts next, Terraform later | Console-only setup |
| D1.8 | Gen1 warehouses (`GENERATION = '1'`) | Gen2 bills 1.35x on AWS; small queries bounded by the 60-second minimum don't recover that; candidate for the measured optimization | Default Gen2 |
| D1.9 | The initial bootstrap loads Bronze directly from `landing/olist/` with `COPY INTO`, bypassing the contract gate | Unblocks profiling early; the validated Parquet path replaces it later and is reconciled against it | Waiting for the Fargate path before any profiling |
| D1.10 | Bronze stores every data column as VARCHAR plus `_file_name`, `_file_row_number`, `_loaded_at`, `_source_team` | Exact copy with no type rejections (kept 23,995 leading-zero zips intact); every row traceable to a file line; typing happens in Silver | Typed Bronze tables |
| D1.11 | All schemas `WITH MANAGED ACCESS`; extra `GOVERNANCE` schema for policies, tags and `market_access` | Grants only through the schema owner and access roles; policies kept apart from the data they protect | Regular schemas; policies inside Gold |
| D1.12 | Users have `DEFAULT_SECONDARY_ROLES = ()`; permission tests run with `USE SECONDARY ROLES NONE` | Secondary roles defaulting to ALL made every role test pass for the wrong reason | Default secondary roles ALL |
| D1.13 | Account ID, external ID and role ARNs stay out of the repo (runtime lookups, script arguments, SQL placeholders) | The repo can go public without exposing account identifiers | Hard-coded values |
| D1.14 | Cortex Analyst is used only through agents or CoWork | The AI quota covers agents and CoWork but not standalone Analyst, so every AI call stays capped | Calling the Analyst REST API directly |
| D1.15 | Feature branches and pull requests for all work after the initial bootstrap, squash merge; branches named by feature (`feature/data-contracts`) | Real review and CI workflow visible in the repo | Committing to `main` throughout |
| D1.16 | Customer-managed KMS key `alias/slussen-data` with yearly rotation and S3 Bucket Key; lifecycle expires noncurrent versions after 30 days | Second lock on the data (S3 + KMS); Bucket Key cuts KMS requests; versioning without growing storage forever | SSE-S3 default encryption; versioning without lifecycle |
| D1.17 | One AWS account: the Organization's management account also holds the workloads | One-person portfolio project; avoids multi-account overhead. Known trade-off against AWS best practice | Separate member account for workloads |
| D1.18 | `DataEngineer` permission set = PowerUserAccess + `iam:PassRole` on `slussen-*` roles + IAM read; tightened later with IAM Access Analyzer policy generation | Resources didn't exist yet; can't change IAM, so it can't escalate itself. Start broad, measure, tighten | Hand-written least-privilege policy upfront |
| D1.19 | `View-Only` permission set uses ViewOnlyAccess, not ReadOnlyAccess | Demos and screen-shares see configuration but no data (no S3 objects) | ReadOnlyAccess |
| D1.20 | SSO session 8 h (default); permission set sessions: AdministratorAccess 4 h, DataEngineer 4 h, View-Only 1 h | One MFA sign-in per working day; leaked role credentials expire within hours | Longer sessions |
| D1.21 | Snowflake integration role is read-only on `landing/olist/*` and `validated/*`, mirrored in `STORAGE_ALLOWED_LOCATIONS` | Snowflake never writes to the lake; `quarantine/` stays out of reach; two independent guards | Bucket-wide read/write |
| D1.22 | Local settings in `.env` (gitignored), keys listed in `.env.example` (committed) | Reproducible setup without committing values | Hard-coded settings |
| D1.23 | Private `notes/` folder gitignored; `docs/` is public | Learning and interview notes stay private; project documentation is part of the portfolio | Everything in the repo |
| D1.24 | Cost guardrails: AWS budget $10/month; Snowflake resource monitor 25 credits/month (hard suspend, warehouses); account root budget 30 credits/month (alerts, all services); AI quota 15/month and 7/day per user with enforcement; Cortex only through `CORTEX_USER_ROLE` (revoked from PUBLIC) | No single control covers warehouses, serverless and AI together | One account-wide limit only |
| D1.25 | Daily work runs with the least-privileged identity: AWS `slussen-de`, Snowflake default role `DATA_ENGINEER`; admin roles only by explicit switch | Mistakes and leaks are limited to what a daily role can do | Admin roles by default |

## Contract gate and event-driven validation

| ID | Decision | Why | Alternative rejected |
| --- | --- | --- | --- |
| D2.1 | One short-lived branch per component, named after it; squash merge only; head branches deleted automatically after merge | `main` reads as one commit per feature; no reused branch names; squashed branches can't be reused by mistake | Merge commits; long-lived or reused feature branches |
| D2.2 | One folder per batch under the date partition: `landing/<team>/<feed>/dt=YYYY-MM-DD/batch=<UTC timestamp>/`; data files are written first and the `_SUCCESS` marker last | Each of several daily batches has its own completeness marker; the trigger fires once per complete batch; reruns target one batch | One `_SUCCESS` per date folder (cannot tell which batch is complete) |
| D2.3 | The validator ships as one container image in ECR (AWS Lambda Python 3.13 base image), used by Lambda and by ECS Fargate with a different entry point; ECR tags are immutable and a lifecycle rule keeps the 5 newest images | The same pinned versions run locally and in AWS; one artifact for both compute paths; 10 GB limit | Managed AWS SDK for pandas layer plus zip (pyarrow version not ours, two packaging methods); hand-built zip with Linux wheels (fragile, near the 250 MB limit) |
| D2.4 | Squash commit messages keep GitHub's `(#N)` pull request suffix | Links every commit on `main` to its review and CI; standard in large open-source projects | Removing the suffix (loses the link; mixed history) |
| D2.5 | `landing/` is a mailbox: after a batch is decided its files are deleted from `landing/`; valid batches are rewritten as Parquet in `validated/`, broken batches are copied unchanged to `quarantine/`; bucket versioning keeps deleted originals for 30 days | `landing/` only shows unprocessed work, so old files there signal a stuck batch; no duplicate storage; recoverable | Keeping originals in `landing/` (grows forever, unclear what is processed) |
| D2.6 | One SNS topic `slussen-contract-alerts` with an email subscription; the address is a script argument, never in the repository; no topic encryption because alerts carry only contract, batch, counts and log path | Owners hear about quarantined batches; no personal data in the alert path; no key policy changes | KMS-encrypted topic (key policy work for no gain); Slack webhook (another secret to manage) |
| D2.7 | The lake bucket's entire notification configuration is declared in one file (`infra/s3/lake_notifications.json`) and applied whole | The S3 API replaces the full configuration on every write, so partial updates silently drop other targets (EventBridge, Snowpipe) | Setting each notification from a separate script |
| D2.8 | The `AUDIT` schema hosts its own load objects (file format, stage, pipe); `AUDIT_RW` holds CREATE FILE FORMAT, STAGE and PIPE, mirroring `BRONZE_RW` | Load objects sit next to the table they load; privileges stay on access roles | Audit stage in `BRONZE` (mixes layers); grants directly to the persona role |
| D2.9 | A quarantined batch ends the state machine in Succeed after alerting; Fail is reserved for the pipeline itself breaking | Failed executions keep a clear meaning: something needs fixing in the pipeline, not in a producer's file | Failing executions for quarantined batches (alerts and dashboards can't tell producer errors from pipeline errors) |
| D2.10 | IAM policies, trust policies and the state machine definition are repository templates with placeholders, rendered at deploy time into a temporary file; one narrow role per component (Lambda, state machine, EventBridge, Snowflake integration) | No account IDs or ARNs in the repository; every permission is reviewable in Git; least privilege per component | Policies written inline in scripts; one shared role |
| D2.11 | All-or-nothing batches: one breaking violation in any file quarantines the whole batch | Bronze never holds half a batch; producers resend a complete batch | Loading the valid files of a partly broken batch |
| D2.12 | Violation records are capped at 10 rows per rule and column per file and never contain record values (rule, column, row index, expected and actual type only) | A drifted file can't flood the audit table or alerts; no personal data reaches the audit schema, which more roles can read | One row per bad record; including the offending values |

## Capacity, historical backfill and lake ingestion

| ID | Decision | Why | Alternative rejected |
| --- | --- | --- | --- |
| D3.1 | When the violation cap drops findings, the gate writes one summary row per capped rule and column (`severity = 'info'`, `row_number` NULL, count in `detail` and in a numeric `suppressed_count` column); `GateOutcome` gains `suppressed`, and breaking + warnings + suppressed equals all findings | The cap hides detail, not volume; the audit table reconciles with the gate outcome in plain SQL; changed before the audit Snowpipe existed | Count only in the `detail` text (fragile parsing); summary row with the original severity (inflates breaking counts) |
| D3.2 | Shared test fixtures live in `tests/conftest.py` (`contracts_dir`, `ops`, `make_ops_record`); helpers used by one file stay in that file | Removes duplicated record builders that could drift apart | Moving every repeated line; deferring the cleanup |
| D3.3 | Batches over 50 MB (50,000,000 bytes) are validated on ECS Fargate; the gate Lambda stays at 1,024 MB | Capacity test: memory ≈ 160 MB + 8.2 × input MB, limit about 105 MB, failing as a timeout at the memory cap; 50 MB keeps peak memory near 55% (`docs/gate_capacity.md`) | Raising Lambda memory (higher cost for every batch); keeping the 100 MB placeholder (above the measured limit) |
| D3.4 | One contract per Olist table (`contracts/olist_<table>.yaml`), each with its own landing prefix and batch folders | The gate already selects a contract by landing prefix; tables version independently; same pattern as the live feeds | One contract with a tables section |
| D3.5 | Logical type `timestamp_ntz` for sources that state no time zone; Parquet stores it without a zone, Snowflake as `TIMESTAMP_NTZ`; the zone assumption is applied in Silver | A contract states only what the producer guarantees; the assumption lives in one visible, testable place | Converting from São Paulo time in the reader; declaring the values UTC |
| D3.6 | A contract may declare `primary_key: []` when the source has no natural key; the duplicate-key rule is skipped. Used only for `olist_geolocation` | 261,831 of 1,000,163 rows are exact duplicates; Bronze stays an exact copy; deduplication belongs in Silver | Deduplicating in the gate; a key on all columns; leaving the table out |
| D3.7 | Fargate tasks run in the default VPC's public subnets with a public IP and a security group with no inbound rules and TCP 443 outbound only | Zero idle cost for occasional large batches; IAM and TLS protect every call; moving to private subnets with VPC endpoints changes only the network configuration | VPC endpoints (about $30/month idle); NAT gateway (about $35+/month) |
| D3.8 | The Fargate task reports the gate outcome to Step Functions with a task token (`runTask.waitForTaskToken`, `SendTaskSuccess` / `SendTaskFailure`) | Both routes return the same outcome, so `CheckOutcome` and the alerts are shared; standard pattern | Writing the outcome to S3 and reading it in an extra state; inferring the outcome from markers |
| D3.9 | Bronze tables for gate-validated files are typed from the contracts (decimals, timestamps, integers; arrays as `VARIANT`) plus file metadata; the initial VARCHAR tables were kept only for reconciliation. Supersedes D1.10 for all gated data | Bronze is an exact copy of what passed the gate; types are already proven, so Silver doesn't re-parse strings | Reloading the VARCHAR tables; one `VARIANT` column per table |
| D3.10 | Bronze tables and Snowpipes are generated from the contracts (`pipeline_core.snowflake_ddl`), committed, and kept in sync by a test | One source of truth for gate, Parquet and Snowflake; no drift, no hand-typed DDL | Hand-written SQL per table |
| D3.11 | The EventBridge rule also matches `landing/olist/*/_SUCCESS`; historical batches trigger the gate like any feed | One event-driven path for every feed; the backfill exercised the real trigger | Starting executions by hand |
| D3.12 | After reconciliation (18 of 18 checks equal), the initial bootstrap load was retired: bootstrap tables, CSV stage and file format dropped; Snowflake's storage integration and IAM policy narrowed to `validated/` and `audit/contract_violations/`; bootstrap scripts removed; raw CSVs deleted from landing. Supersedes D1.9, narrows D1.21 | One way into Bronze; Snowflake reads only gate-approved data; landing stays a mailbox | Keeping everything until Silver is built; keeping VARCHAR copies without a purpose |
| D3.13 | Glue tables for `validated/` are Athena DDL generated from the contracts (`pipeline_core.athena_ddl`), with partition projection on `dt` and a sync test; queries run in an enforced workgroup with encrypted results and a 1 GB per-query scan limit | One source of truth for gate, Snowflake and the lake catalog; exact types; partitions appear without registration; no crawler cost | Glue crawler (cost, inferred types, re-crawls); hand-written DDL (drift) |

## Duplicate deliveries, dependency pinning and continuous integration

| ID | Decision | Why | Alternative rejected |
| --- | --- | --- | --- |
| D4.6 | A re-upload into a batch that is already decided (marker in `validated/` or `quarantine/`) is moved as sent to `quarantine/<feed>/_duplicates/dt=…/batch=…/received=<timestamp>/`, recorded as a `duplicate_batch` warning in its own audit file, and alerted by email (state `BatchDuplicate`, a Succeed state); a duplicate event whose landing files are already gone is skipped silently; a scheduled check flags any object left in `landing/` longer than an hour | Delivery is at-least-once and producers retry; nothing is lost silently, landing stays empty at rest, the original decision is never overwritten, and the producer learns to re-send corrections under a new batch id | Deleting the re-upload (a corrected re-send could vanish); leaving it in landing (landing never empties); relying on producers to check first (manual cleanup, no protection from other teams) |
| D4.9 | Python dependencies are pinned with pip-tools in two hashed lock files generated from `pyproject.toml`: `requirements.lock` (runtime) for the validator image and `requirements-dev.lock` (runtime + tests) for CI and local development; both install with `--require-hashes`; the image installs the lock in its own layer before the package (`--no-deps`) | The same commit always builds the same image; a tampered or swapped package is refused; dependency layers stay cached across code changes | Version ranges only (each build takes whatever is newest); one lock for everything (test tools in the Lambda image); uv (a second package manager next to pip) |
| D4.12 | The ops generator seeds its random generator from seed and batch time (`"<seed>:<batch time>"`) | A seed reproduces one batch exactly, while different batch times produce different orders; two batches with the same seed had contained the same 50 records with shifted timestamps | Seed only (identical batches); deriving only the event id per batch (every batch would still contain the same orders) |
| D4.13 | The gate Lambda timeout is 60 s, applied by the deploy script on every deploy together with memory | The slowest batch that can reach Lambda (46.5 MB) takes 8.85 s warm and about 20 s with a cold start, leaving three times headroom; Lambda bills actual duration, so only a run stuck at the memory cap is affected, and its failure alert arrives within a minute | 300 s (slow failure signal); 30 s (too little headroom for a cold start) |
| D4.14 | The lake bucket's lifecycle configuration lives in `infra/s3/lake_lifecycle.json` and is applied whole by its own script: noncurrent versions expire after 30 days, incomplete uploads after 7, expired delete markers are removed, and `athena-results/` expires after 7 days | S3 replaces the whole lifecycle configuration on every write, so it must be declared in one reviewable file; query results are copies of lake data outside the governed zones; delete markers from landing cleanups would otherwise pile up forever | Adding a rule from the command line (silently drops the existing rule, not in Git); keeping query results indefinitely |
| D4.15 | CI scans every committed file for account identifiers with two layers: generic patterns (any ARN or ECR host containing a 12-digit account number) and the exact account ID from a repository secret, masked in logs; a missing secret fails the job | Catches identifiers in templates, docs and prose without storing the account ID in the repository; the job fails closed instead of passing silently | Generic patterns only (a bare account ID would pass); the account ID in the repository |
| D4.16 | GitHub Actions are pinned by full commit SHA (version kept as a comment, releases older than about two weeks preferred); the workflow token is read-only, checkout keeps no credentials, and CI holds no AWS or Snowflake credentials | A tag can be moved to different code, a commit SHA can't; a compromised step can read but not change the repository, and can't reach the cloud accounts | Version tags (`@v7`); default token permissions; deploying from CI in this phase |

| D4.10 | DAGs are paused at creation, with `catchup=False`, so unpausing creates only the latest due run; the check DAG runs 15 minutes after each ops batch | Nothing runs or costs money until switched on deliberately, with no surprise backlog; the checks see the batch after Snowpipe has loaded it and share one warehouse wake-up with the producer's load-log write | Active at creation; catchup; checks on their own unrelated schedule |
| D4.11 | Compose project `slussen` publishes only `127.0.0.1:8081`, no database port | Coexists with another local Airflow on 8080; not reachable from the LAN | Default `0.0.0.0:8080` |

| D4.18 | Contracts baked into the Airflow image at `/opt/slussen/contracts` | The image tag pins the contract version the DAGs use, the same way the gate image does | Bind-mounting `contracts/` (DAGs could run against contracts the gate doesn't have) |

## Platform checks, deploy scripts and data cleanup

| ID | Decision | Why | Alternative rejected |
| --- | --- | --- | --- |
| D4.5 | Check severity: `error` fails the check run, `warn` only records. Cross-batch `event_id` collisions, `landing/` not empty at rest and reconciliation mismatches are `error`; known, accepted conditions are `warn` | A broken invariant has to turn the run red; accepted conditions (legacy ops items, the one Olist order without a payment) stay visible without failing every run | Every finding fails (permanently red, so real failures drown); nothing fails (findings only seen when someone looks) |
| D4.8 | The deploy scripts (upload a batch, start a gate execution, inspect the latest execution, push the validator image) get Bash versions next to the cmd versions, linted by ShellCheck in CI; the bootstrap scripts stay cmd until Terraform replaces them | Deploy scripts run often and have to work on Linux and in CI; bootstrap scripts ran once and are better replaced than ported | Porting every script; Python for the CLI glue |
| D4.26 | One check DAG, `platform_checks`, with three task groups (reconciliation, freshness, data quality); each Snowflake task opens one connection | One place to see platform health; one warehouse wake-up per run; the groups pass or fail independently in the run view | Three separate check DAGs |
| D4.27 | Lake reconciliation covers only the tables the Airflow role can already read (`ops_orders`, `olist_order_items`, `olist_customers`): row counts, distinct keys and money sums in Athena vs Snowflake; Glue read is granted per table, and query results stay in the enforced workgroup's `athena-results/` | Athena reads S3 with the caller's own credentials, so every reconciled table widens the role's data access; these three cover the live feed and two history tables, including money | Read access to all of `validated/` for the Airflow role |
| D4.28 | A freshness status of `late` or `no_data` fails the check run. Hourly SLAs are a maximum age; a weekly deadline counts a load from 24 hours before the latest passed deadline onwards; one-off backfills are not applicable | An SLA breach is exactly what the check exists to flag; a window tied to the deadline fits a weekly cadence better than a fixed age | Recording only; a fixed 7-day maximum age for the weekly feed |
| D4.29 | The unknown-product check covers ops rows loaded in the last 24 hours | Early ops batches used random product ids and stay in Bronze; over the full history the check would fail on every run and hide new regressions; 24 hours measures the producer as it is now | Full Bronze history |
| D4.30 | Duplicate data found by the checks is removed from `validated/` and from Bronze in the same change; the copy's data files go, its `_SUCCESS` marker stays | Both stores stay reconciled; the marker keeps the batch decided, so a later re-upload under that id is still parked as a duplicate; deletes stay recoverable through bucket versioning (30 days) and Time Travel | Deleting the marker too (the batch id becomes reusable); cleaning only Bronze (the reconciliation breaks) |


## Silver, Gold and governance

| ID | Decision | Why | Alternative rejected |
| --- | --- | --- | --- |
| D5.0 | Backfills cover the producer DAGs only; `platform_checks` is triggered once after a backfill instead of being backfilled | A check run for a past slot tests today's data, not that slot's data | Backfilling `platform_checks` slots |
| D5.1 | GMV = sum of item price + freight for orders that are not `canceled` or `unavailable`; delivered GMV is a separate measure; payment totals are not used for GMV | Item value is what was sold; payment totals include installment interest and vouchers | GMV from payment totals |
| D5.2 | The two categories missing from the translation table get English names from a small override table; products without a category become `unknown` | Readable English names everywhere; the source table stays untouched | Portuguese fallback names |
| D5.3 | Olist dates shift by whole days to an anchor (see D5.15); the analysis window starts at the shifted 2017-01-01; Olist orders after the anchor month are flagged `is_post_anchor_history` | The sparse 2016 months and the Sep/Oct 2018 tail distort trends; whole weeks keep weekdays | A fixed offset unrelated to the live feed |
| D5.4 | Olist `timestamp_ntz` values are Sao Paulo wall time (applied as in D5.12) | The source is a Brazilian marketplace and states no zone | Treating them as UTC |
| D5.5 | Silver keeps the latest ops snapshot per `order_id`, ordered by `event_ts` then `event_id` | Each event repeats the full order; the order is deterministic | First snapshot; a status-rank rule |
| D5.6 | Silver and Gold objects are owned by `DATA_ENGINEER` | Same owner as Bronze, one role to reason about | `TRANSFORM_ROLE` as owner (kept for a later separation of duties) |
| D5.7 | Silver dynamic tables use `TARGET_LAG = DOWNSTREAM`; Gold sets the lag (D5.21) | Silver refreshes only when a Gold table needs it | Scheduled Silver refreshes |
